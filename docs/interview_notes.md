# 面试讲解稿与追问准备

## 30 秒项目介绍

我把自己熟悉的《无畏契约》抽象成一个竞技游戏核心模块测试项目。先按业务风险把对局状态、回合结算、局内经济和断线重连列为高优先级，再用 Python/pytest 建立可配置领域模型。当前实际收集122个参数化自动化场景，覆盖技能伤害边界、接口契约以及延迟、丢包、重复包和乱序，并用10万条模拟事件验证日志分析。项目重点不是复刻游戏客户端，而是验证服务端权威、幂等和数据一致性这些高风险质量属性。

## 为什么采用状态机

对局不是一组互不相关的页面，而是有严格先后关系的状态集合。状态机可以同时表达允许路径和非法跳转，让需求、测试用例与代码共享同一套状态定义。它特别适合发现“卡在中间态”“重复结算”“跳过必要阶段”这类缺陷。

## 为什么不做 UI 自动化为主

UI 自动化成本高、易受分辨率和版本改动影响，而且很难直接定位资产或结算不一致。本项目先把高风险规则下沉到稳定的模型/API 层，只在真实项目中保留少量端到端冒烟。测试金字塔能更快反馈，也更容易纳入 CI。

## 为什么重复请求是重点

真实网络可能超时、重试或乱序。客户端没收到响应，不代表服务端没执行。如果没有 request_id 和幂等处理，一次购买或结算可能执行两次。因此测试不仅看返回值，还核对余额、库存、比分和交易记录是否只变化一次。

## 断线重连怎样测

在购买、战斗、回合结束等关键阶段分别注入断线；修改客户端本地快照来模拟旧数据；重连后检查阶段、回合号、比分、资产和玩家状态，以服务端权威数据恢复；同时验证多次重连和重连超时不会生成重复玩家或重复结算。

## 如果扩展为企业级项目

- 将模型替换为真实 HTTP/WebSocket/RPC 接口，并做 Schema/错误码契约校验。
- 用代理注入延迟、丢包、断网和乱序，覆盖多地域网络。
- 用 k6/Locust 对匹配、结算和日志链路做分层压测，关注 P95/P99、错误率和资源利用率。
- 将 pytest 接入 CI，P0 用例作为发布门禁，失败时自动关联日志和请求链路。
- 针对版本改动维护风险矩阵，只回归受影响模块加核心主链路。

## 不能说过头的边界

- 可以说：基于公开玩法和个人体验建立测试模型，完成自动化验证。
- 不可以说：测试过拳头/腾讯生产接口、发现过线上官方缺陷、掌握官方内部规则实现。
- 指标必须以本地测试报告为准，不编造覆盖率或缺陷数量。
- 122指pytest收集的参数化场景，不要说成122个独立函数；10万条是模拟事件，不是真实玩家日志。

## 高频追问

**为什么不是直接自动操作游戏客户端？** 公开客户端无法提供稳定、合规的内部接口和测试环境，直接做脚本还可能触碰反作弊。本项目选择在自建模型中证明测试设计、接口契约、状态机和故障注入能力，不对真实客户端进行注入或绕过。

**网络模拟和真实弱网有什么区别？** 当前通道是确定性故障模型，优点是CI可重复，能验证业务对重复和乱序的处理；真实项目还要用网络代理或设备注入抖动、带宽限制和随机丢包，并结合客户端、网关和服务端指标分析。

**为什么10万条日志的内存很低？** 输入使用生成器逐条产生，分析器只保留固定半径的前文窗口、待补全上下文和错误结果，而不是把全部记录读入列表。因此内存主要与上下文半径和错误数量相关，而非总行数。
