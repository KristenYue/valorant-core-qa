# 竞技游戏核心模块测试方案

## 1. 项目边界

本项目根据玩家可观察到的竞技游戏流程建立测试模型，不代表拳头游戏或腾讯内部实现，也不调用非公开接口。武器价格、胜负规则等易变配置不硬编码为“官方真值”；自动化关注可迁移的不变量、状态转换和异常恢复。

## 2. 风险排序

| 优先级 | 模块 | 核心风险 | 主要测试手段 |
|---|---|---|---|
| P0 | 对局主流程 | 卡死、非法跳转、无法结算 | 状态机、端到端场景 |
| P0 | 回合结算 | 重复加分、分数不一致 | 幂等测试、服务端权威状态 |
| P0 | 断线重连 | 客户端与服务端状态不一致 | 故障注入、快照恢复 |
| P1 | 购买与退款 | 负余额、重复扣款、非购买阶段购买 | 边界值、等价类、幂等测试 |
| P1 | 技能与伤害 | 重复伤害、死亡后施法、护甲边界错误 | 边界值、状态检查、事件幂等 |
| P1 | 接口契约 | 字段缺失、类型/版本变化破坏客户端 | Schema与兼容性测试 |
| P1 | 网络传输 | 丢包、重复包和乱序造成状态不一致 | 确定性故障注入矩阵 |
| P1 | 日志可观测性 | 故障发生但无法定位 | JSONL 清洗、错误上下文提取 |
| P2 | 性能 | 峰值排队和日志量导致延迟 | 分层压测方案、离线规模测试 |

## 3. 质量准入标准

- P0 用例通过率 100%，不存在阻断主流程或破坏分数/资产一致性的缺陷。
- 同一请求重复发送不会重复扣款、重复加分或重复发放奖励。
- 非法状态转换必须被拒绝，并留下可定位的错误信息。
- 断线重连后以服务端快照为准，回合、阶段、比分保持一致。
- 购买成功满足：余额变化 + 库存变化 + 交易日志三者一致；失败不产生副作用。
- ERROR 日志至少包含时间、事件名和关键业务标识，可提取相邻上下文。

## 4. 自动化分层

1. **单元/模型层**：经济规则、状态转换、幂等逻辑，运行快，作为提交门禁。
2. **服务/API 契约层（本项目用领域方法模拟）**：输入校验、错误码、重复请求、服务端权威数据。
3. **端到端层**：排队→选人→加载→购买→战斗→结算，只保留少量核心冒烟链路。
4. **非功能层**：弱网/断线、并发和大日志量；生产项目中应由独立环境和专项工具执行。

当前仓库通过参数化共收集122个自动化场景。其中网络矩阵覆盖4档延迟、2档丢包、2档重复包和2档乱序窗口。规模测试使用10万条明确标注为“模拟”的事件，不冒充真实玩家或生产数据。

## 5. 缺陷示例及定级

- S1/P0：重复回合结算事件导致比分增加两次。
- S1/P0：重连后使用客户端旧比分覆盖服务端比分。
- S2/P0：加载失败无法退出或重试，玩家卡在中间态。
- S2/P1：重复购买请求导致二次扣款。
- S3/P1：错误日志缺少 match_id，无法串联故障链路。

严重程度描述影响，优先级描述修复紧迫性，二者不能混用。
